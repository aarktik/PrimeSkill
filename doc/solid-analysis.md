## ขอบเขตและข้อสรุป

เอกสารนี้อธิบายหลักฐานที่มีในโค้ดปัจจุบันตามหลักการทั้งห้า ไม่ใช่การรับรองว่าไม่มีการละเมิดทุกข้อทั่วระบบ การตรวจอ่านครอบคลุมขอบเขต controller/service/repository, service interfaces, mapper, search strategies, publishing states, events และการค้นหา injection/UnsupportedOperationException ใน production Java แต่ยังไม่ได้พิสูจน์ทุกเส้นทางด้วย contract tests แยกสำหรับ SOLID

## ข้อจำกัดที่ต้องเปิดเผยและงานถัดไป

1. **OCP:** [service/impl/ToolSearchServiceImpl.java:53](https://github.com/aarktik/PrimeSkill/blob/4678e0047184de7100579041c9cdfacfe228c688/code/src/main/java/com/example/toolhub/service/impl/ToolSearchServiceImpl.java#L53) และ relevance branch ในคลาสเดียวกัน ยังต้องแก้ Service เมื่อเพิ่ม query policy แบบพิเศษ ควรย้าย query execution ไปยัง strategy โดยรักษา rating ก่อน pagination, id tie-break และ relevance fallback
2. **SRP:** [service/impl/ToolVersionServiceImpl.java:125](https://github.com/aarktik/PrimeSkill/blob/4678e0047184de7100579041c9cdfacfe228c688/code/src/main/java/com/example/toolhub/service/impl/ToolVersionServiceImpl.java#L125) และ [service/impl/ToolVersionServiceImpl.java:117](https://github.com/aarktik/PrimeSkill/blob/4678e0047184de7100579041c9cdfacfe228c688/code/src/main/java/com/example/toolhub/service/impl/ToolVersionServiceImpl.java#L117) ยังรวม DTO mapping และ version input normalization ใน Service; แยก mapper/format policy ได้หากดำเนิน refactor ต่อ Business invariants เช่น ownership และ draft-only เป็นหน้าที่ของ Service/domain ไม่ใช่ข้อผิดพลาดเพียงเพราะเป็น validation
3. **DIP:** concrete mappers และ state machine ควรมีสัญญาเฉพาะงานหากต้องผ่านเกณฑ์ interface-only; ไม่สร้าง interface ที่ไม่มีเหตุผลทางหน้าที่เพียงเพื่อเพิ่มจำนวนคลาส
4. **LSP/ISP:** หลักฐานโครงสร้างยังไม่ใช่การพิสูจน์ครบทุก implementation/consumer ต้องตรวจสัญญา input/output/error และเพิ่ม contract tests เมื่อปรับโครงสร้าง
5. EntityManager.refresh และ row locks มีไว้รักษา concurrency; ห้ามลบเพียงเพื่อทำให้ Service ดูสั้นลง
